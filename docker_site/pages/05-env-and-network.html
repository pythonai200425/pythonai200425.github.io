🔌 Chapter 05

Env Variables & Networks

Configure containers without rebuilding images using environment variables, and wire multiple containers together using Docker networks with automatic DNS resolution.

🎯
Chapter Goal
Pass runtime config with -e flags, create a user-defined network, and connect containers so they can reach each other by name — no IP addresses needed.

A Environment Variables

Environment variables let you change a container's behavior at runtime — no image rebuild needed. This is the standard way to pass database passwords, API keys, ports, and modes.

bash
# Set two env vars and print them
docker run --rm -e APP_MODE=dev -e APP_PORT=9000 alpine sh -c 'echo "$APP_MODE $APP_PORT"'

Expected output: dev 9000

Load from a .env file

Instead of listing vars one by one, put them in a file:

bash
# Create .env file
echo "APP_MODE=production
DB_HOST=localhost
DB_PORT=5432" > app.env

# Pass entire file at once
docker run --rm --env-file app.env alpine sh -c 'echo "$APP_MODE"'
⚠️
Never bake secrets into images
If you put a secret in a Dockerfile instruction like ENV DB_PASSWORD=secret, it's visible in the image history forever. Always inject secrets at runtime via -e or --env-file.

B Docker Networks

By default, containers are isolated. To let them talk to each other, put them on the same user-defined network. Docker's built-in DNS will resolve container names to IP addresses automatically.

  ┌─────────────────────────── appnet ──────────────────────────────┐
  │                                                                  │
  │   ┌──────────────┐     DNS: "redis1"     ┌──────────────────┐  │
  │   │   app        │──────────────────────▶│   redis1         │  │
  │   │   container  │                       │   (Redis server) │  │
  │   └──────────────┘                       └──────────────────┘  │
  │                                                                  │
  └──────────────────────────────────────────────────────────────────┘

  Containers on the same user-defined network resolve each other by NAME.
  Default bridge network does NOT have this DNS feature.

Step 1 — Create a network

bash
docker network create appnet

Step 2 — Start Redis on the network

bash
docker run -d --name redis1 --network appnet redis

Step 3 — Connect from another container using the DNS name

bash
docker run --rm --network appnet alpine sh -c \
  "apk add --no-cache redis && redis-cli -h redis1 ping"

Expected output: PONG — the second container reached Redis by its container name, not by IP!

ℹ️
Why user-defined networks?
The default bridge network only allows communication by IP. User-defined networks add DNS so containers resolve each other by name. Docker Compose creates a user-defined network automatically — that's why services find each other by service name.

Docker Network Types

DriverUse CaseContainer-to-Container?
bridgeDefault for standalone containersBy IP only (no DNS)
user-defined bridgeMulti-container appsYes, by name (DNS) ✓
hostMax performance, Linux onlyShares host network stack
noneComplete isolationNo networking at all

Cleanup

bash
docker rm -f redis1
docker network rm appnet
🧪

Quick Exercise

  1. Create a network called testnet.
  2. Start two Alpine containers on that network with different names: node-a and node-b.
  3. From node-a, ping node-b by name: docker exec node-a ping -c 3 node-b.
  4. Try the same ping from a container on the default bridge network — it should fail.
  5. Run docker network inspect testnet to see which containers are attached.
