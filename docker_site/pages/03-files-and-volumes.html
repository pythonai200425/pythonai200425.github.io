📁 Chapter 03

Files & Volumes

Containers are isolated — but data must flow in and out. Learn the three methods for sharing files between your host and containers, and how to persist data beyond a container's lifetime.

🎯
Chapter Goal
Master docker cp for one-off transfers, bind mounts for live host-folder access, and named volumes for data that must survive container deletion.

Three Methods at a Glance

📋

docker cp

One-time file copy in or out of a container. Simple but not live — won't sync changes.

🔗

Bind Mount

Link a host folder directly into the container. Changes sync instantly in both directions. Great for development.

💾

Named Volume

Docker-managed storage that persists when containers are deleted. Best for databases and important data.

A Copy Files with docker cp

Use docker cp when you need to get a file in or out of a running or stopped container — think of it like scp for containers.

Step 1 — Create a test file on your host

bash
echo "hello from host" > note.txt

Step 2 — Start a long-running container

bash
docker run -d --name filebox ubuntu sleep 3600

Step 3 — Copy the file in, then read it back

bash
# Copy FROM host TO container
docker cp note.txt filebox:/tmp/note.txt

# Verify inside the container
docker exec -it filebox cat /tmp/note.txt

# Copy FROM container back to host
docker cp filebox:/tmp/note.txt ./recovered.txt

B Bind Mount a Host Folder

With -v HOST_PATH:CONTAINER_PATH, the container and host share the same folder in real time. This is the go-to method during development — edit a file on your host and the container sees it immediately.

bash
# Mount current directory into /work inside the container
docker run --rm -it -v ${PWD}:/work ubuntu bash

Inside the container:

bash (inside container)
ls /work        # your host files appear here
echo "from container" >> /work/new-file.txt
exit

Back on your host, check — new-file.txt exists! Changes are instant and bidirectional.

⚠️
Container user permissions
Files created inside a container may be owned by root. On Linux this can cause permission issues on the host. Use --user $(id -u):$(id -g) to match your host user.

C Named Volumes (Persistent Data)

Named volumes are managed entirely by Docker. They survive container deletion and can be shared between multiple containers. Perfect for database data.

bash
# Create the volume
docker volume create mydata

# Write data into the volume via a temporary container
docker run --rm -v mydata:/data ubuntu bash -c "echo saved > /data/test.txt"

# Read data back via a DIFFERENT container — data persists!
docker run --rm -v mydata:/data ubuntu cat /data/test.txt
ℹ️
Where volumes live on disk
On Linux: /var/lib/docker/volumes/. On Docker Desktop (Mac/Windows): inside the VM. You don't need to know the path — Docker manages it. Use docker volume inspect mydata to see details.

Manage Volumes

bash
docker volume ls            # list all volumes
docker volume inspect mydata # details
docker volume rm mydata      # delete volume (must not be in use)

When to Use Which?

MethodBest ForSurvives Container Delete?
docker cpOne-time debug or file recoveryN/A (manual copy)
Bind mountDevelopment — live code editingYes (it's a host path)
Named volumeDatabase files, production dataYes (Docker-managed)

Cleanup

bash
docker rm -f filebox
docker volume rm mydata

Quick Exercise

  1. Create a volume called pgdata-demo.
  2. In one container, write two lines of text to /data/log.txt inside the volume.
  3. In a completely separate container (different container ID), read the same file back.
  4. Delete the first container. Confirm the data still exists in the volume.
  5. Try using docker volume inspect pgdata-demo to find the mount point.
